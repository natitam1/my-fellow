presence:{id} EX 120 as the hot store and flush to Postgres periodically to avoid write

amplification).
online = showPresence && now - lastSeen < 2 min . Respect show_presence=false (return
null ). Don't leak presence of blocked users.

Lists include presence only where the UI shows it (suggestions, followers list).

9.5 Search
People: ILIKE /trigram on username and unaccent(lower(display_name)) using the GIN
trigram indexes; rank exact/prefix first, then similarity, then follow-graph proximity (people I follow
rank higher).
Posts: Postgres full-text search ( to_tsvector('simple', body) + websearch_to_tsquery )
with visibility/block filters, recency-weighted. (Use the simple config unless you add languagespecific handling. Amharic isn't covered by built-in stemmers.)
Hashtags: parse #tags on create into hashtags/post_hashtags ; GET /trending/tags = tag
counts in the last 24 to 48 h (cached 5 min).
Autosuggest GET /search/suggest?q= returns top users + tags, debounced on the client, with a
minimum 2-char query and tight rate limit.
Add Meilisearch/Typesense only if Postgres search measurably can't keep up.

10. Posts, threads, feeds, and the rest of the content domain
10.1 Creating posts (the write path)
POST /posts (Idempotency-Key) in one transaction: validate (length ≤ 500 grapheme-aware, body-

or-media required, max 4 media, replyToId / quotedId visible to the viewer and not blocked) →
insert post (set root_id for replies) → link media (verify ownership/ ready ) → parse mentions &
hashtags (resolve usernames → post_mentions ; mentions of users who blocked the author are
ignored) → increment posts_count (for non-replies) and the parent's reply_count / quoted post's
quote_count / reposted post's repost_count → outbox post.created (feeds fan-out, notifications

for mentions/replies/quotes, search). Return the hydrated Post .
Edit: within the edit window only, re-parse mentions/hashtags, set edited_at . Delete: soft delete
+ decrement counters + enqueue cleanup (remove from timelines/notifications/search).
Reposts: PUT /posts/:id/repost creates a kind='repost' row (unique per user/original).
Reposting a repost resolves to the original. A repost shows in followers' feeds as "Abenezer
reposted" with the original post embedded.
Content rules: profanity/spam heuristics (rate + duplicate-content + link-count checks), per-user
post limit (e.g. 50/day), shadow-limit on new accounts. Hook for a moderation provider later.

10.2 Thread view
GET /posts/:id/thread → { ancestors: Post[] (root → parent), focus: Post, replies: {
items, nextCursor } } . Replies ordered by created_at asc (or "top" by like_count later). Use
root_id to fetch an entire conversation efficiently. Deleted ancestors/replies appear as tombstones

so threads don't break.

10.3 Feeds (the read path)
Following feed ( /feed/following ): posts by people I follow + my own, excluding replies,
blocked/muted authors, deleted, and visibility-restricted content; reposts surface the original
(dedupe: if both original and repost appear, show once, keeping the earliest relevant time).
select p.id, p.created_at
from posts p
where p.deleted_at is null
and p.kind in ('post','repost','quote')
and (p.author_id = $viewer or p.author_id in (select followee_id from follows
where follower_id = $viewer and status='accepted'))
and not exists (select 1 from blocks b where (b.blocker_id=$viewer and
b.blocked_id=p.author_id) or (b.blocker_id=p.author_id and b.blocked_id=$viewer))
and not exists (select 1 from mutes

m where m.muter_id=$viewer and

m.muted_id=p.author_id)
and (p.created_at, p.id) < ($cursorTs, $cursorId)
order by p.created_at desc, p.id desc
limit $limit + 1;

Two-step: (1) fetch ordered ids, (2) hydrate by id = ANY($ids) (authors, media, counts,
repost/quote embeds, viewer state with one query each for likes/bookmarks/reposts) and restore
order. limit+1 tells you hasMore .
Scaling model (explain it in an ADR): at campus scale, fan-out-on-read (the query above) with the
posts_author_time index is fast and simple. Put the feed behind a FeedProvider interface so you

can later switch to fan-out-on-write ( timeline_entries(user_id, post_id, created_at) filled by
the outbox worker, with a hybrid "pull for high-follower accounts" rule) only if measurements show
p95 > target. Add the measurement (k6 script + EXPLAIN output) to the ADR.
For You feed ( /feed/for-you ): candidate generation (recent posts from followed users + posts
from friends-of-friends + high-engagement recent posts from the fellowship) → filter (same
predicates as above + dismissed/ not interested ) → rank: score = log1p(likes·1 + replies·2
+ reposts·3) · recencyDecay(age, halfLife≈12h) · affinity(author) + a small exploration

term → dedupe/diversify (max 2 consecutive posts per author) → hydrate. Keep ranking in one pure,
unit-tested function so it's explainable ( debug=1 for admins returns score components). Use a
stable per-session seed + cursor that encodes the rank snapshot so pagination doesn't reorder.

New-post indicator: GET /feed/head?since=<newest cursor> returns { newCount } (cheap
count capped at 50) for the "N new posts" pill; the client refetches page 1 on tap or pull-to-refresh.

10.4 Counters, likes, bookmarks (hot path)
PUT /posts/:id/like : INSERT … ON CONFLICT DO NOTHING RETURNING → if inserted:
like_count+1 , outbox like.created (notification for the author, de-duped/aggregated: "Hiwot

and 3 others liked your reflection"). DELETE mirrors without notification. Response: { liked:
true, likeCount } .

Bookmarks are private (never visible to others, count not exposed). Bookmark state is part of
viewer .

Likes tab privacy: default only the owner sees their likes (configurable).

10.5 Fellowship domain: ministries, events, highlights, content library
Ministries/events: GET /profiles/:username/ministries returns memberships (name, role,
"Active" status) and the user's upcoming events (expand recurrence_rule server-side for the
next N occurrences in the user's timezone; store RRULE, don't store every occurrence).
Admin/leaders manage ministries/events (role checks). Event reminders connect to the app's
local-reminders feature via GET /events data; optionally push "starting soon" via a scheduled
job.
Highlights: CRUD for the owner (max ~10 highlights, ≤ 20 items each). Items reference posts or
assets; a cover asset is required. Deleting a post nulls the item ( ON DELETE SET NULL ) and a
cleanup job removes empty highlights.
Content library (home videos): GET /content/videos?cursor= ordered by published_at desc ;
admin-curated; list item = { id, title, description, durationSeconds, thumbnail:
MediaRef, playbackUrl? } . Cache with ETag + short TTL. Watch progress (optional later).

10.6 Streaks (the flame chip and "32d Streak" badge)
Definition (put it in an ADR): a qualifying action (daily check-in; optionally opening the app,
reading a devotional, or posting) counts for the user's local calendar date ( profiles.timezone ,
default Africa/Addis_Ababa ).
POST /streak/check-in is idempotent per local day: compute localDate on the server from
now() + timezone (never trust a client date), INSERT INTO streak_days … ON CONFLICT DO
NOTHING RETURNING ; if inserted, update user_streaks : current = (last_local_date ==
localDate - 1) ? current + 1 : 1 , longest = max(longest, current) , last_local_date =
localDate . Return { current, longest, checkedInToday } .

Reading the streak: if last_local_date < localToday - 1 then the displayed current streak is 0
(broken) even before the nightly rollup. Optional grace/freeze token as a later feature.
DST isn't an issue in Ethiopia, but use a proper tz library ( Intl / date-fns-tz / luxon ) so other
timezones work.

Nightly job: persist broken streaks, award milestone notifications (7/30/100 days).

11. Notifications, push, and background jobs
11.1 In-app notifications (bell badge + inbox)
Created only by workers consuming outbox events (never inline in request handlers). Types:
follow , like , reply , mention , repost , quote , ministry_announcement ,
streak_milestone , system .

Aggregation: like/repost/follow events upsert on (recipient_id, group_key) (e.g. like:post:
<id> ), push the actor into actor_ids (cap 5), bump actor_count , set updated_at , and clear
read_at only if materially new. UI: "Hiwot, Bethelhem and 26 others liked your reflection".

Skip notifications for self-actions, blocked/muted actors, and users who disabled the type.
GET /notifications (cursor on (updated_at, id) ) hydrates actors/entities in batch. GET
/notifications/unread-count is O(1)-ish via the partial index (and cached in Redis; bust on

write/read). /me includes the same count so the bell badge costs no extra request.
POST /notifications/read marks specific/all as read; opening the inbox shouldn't auto-mark

everything read unless that's the product choice.

11.2 Push (Expo Push Service)
1. App registers: getExpoPushTokenAsync → PUT /me/push-devices { token, platform,
appVersion, locale } . Upsert by token; re-assign the token if it's now used by a different user

(shared/test devices); remove on sign-out.
2. Worker builds messages (title/body/ data: { url: '/profile/…' } deep link/ channelId:
'social' / categoryId ), batches ≤ 100 per request via expo-server-sdk , respects preferences

+ quiet hours (user timezone), collapses bursts (don't push 30 likes: send one aggregated push
per post per 10 min).
3. Tickets & receipts: store tickets, poll receipts after ~15+ min; on DeviceNotRegistered mark the
device disabled_at and stop sending. Retry transient errors with exponential backoff.
4. Android channel(s) must exist on the client (the reminders guide already creates one; add a
social channel with a lower importance than reminders).

5. Foreground handling on the client: show an in-app banner and bump the unread badge; tapping
deep-links via data.url (reuse the existing notification response handler).
6. Push is separate from local reminders (offline-first, already built). Don't mix the channels or the
preferences.
